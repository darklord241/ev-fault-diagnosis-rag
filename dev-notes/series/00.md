# Provenance in the Document Pipeline

## Overview of Changes
- Added `provenance.py` to load and normalize metadata from sidecar JSON files.
- Updated the HTML and PDF processors to attach provenance to processed records.
- Updated the chunker to preserve provenance in every generated chunk.
- Added `validate_pipeline.py` to check provenance, data quality, and consistency between processed records and chunks.
- Added unit tests for metadata loading, validation, URL fallback, and provenance preservation.

## Significance
Provenance allows retrieved information to be traced back to its source document. This is important for building a reliable RAG system where answers should be supported by identifiable sources rather than untraceable text.

## New Code and Concepts
- **Sidecar metadata:** Separate JSON files store information about each source document.
- **`pathlib` and `json`:** Used to locate and read metadata files.
- **Custom exception:** `SidecarMetadataError`, derived from `ValueError`, reports invalid or missing metadata.
- **Validation and unit testing:** Required fields are checked for valid values; `vehicle_model` can be `None` when unspecified. `unittest` and `tempfile` are used to test behavior without depending on the actual corpus.

## Alternatives Considered
- Matching metadata by filename was avoided in favor of matching by `document_id`, which provides a more stable link between pipeline stages.
- Provenance could be looked up later during retrieval, but attaching it during processing and preserving it through chunking keeps source information alongside the text.
- A non-empty `final_url` is preferred, with `url` used as a fallback.

## Changes This Brings About
Processed records and chunks now carry the same provenance fields while retaining their existing IDs and text. The validation script can detect missing or inconsistent metadata, duplicate IDs, and broken record-to-chunk relationships.
