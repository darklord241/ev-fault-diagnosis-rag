# Ingestion Pipeline and Data Directory Reorganization

## 1. Purpose

This reorganization establishes a consistent structure for source documents, ingestion scripts, metadata, extracted records, and retrieval chunks in the EV Fault Diagnosis RAG project.

The objectives are to:

- Provide one entry point for all incoming source files.
- Separate original documents from generated artifacts.
- Preserve document provenance and stable document IDs.
- Introduce a central manifest that tracks the complete ingestion lifecycle.
- Make pipeline stages independently testable and safely retryable.
- Detect unsupported formats, missing artifacts, and inconsistent processing states.
- Make future ingestion of additional document formats easier.

## 2. Data Directory Structure

The `scraper/data/` directory contains source documents and ingestion artifacts.

```text
scraper/data/
├── incoming/
├── archived/
├── metadata/
├── processed/
├── chunked/
└── manifest.json
```

### `incoming/`

The single entry point for newly collected source files.

Supported and unsupported files are registered during discovery. Supported formats proceed through the ingestion pipeline, while unsupported formats are recorded with an appropriate status rather than silently ignored.

The directory may contain HTML, PDF, TXT, and other files that may become supported in the future. Collection archives such as ZIP files may also be inventoried, but are not processed as individual documents.

### `archived/`

Stores original source files after the required ingestion stages and validations have succeeded.

Files must not be archived merely because output files exist. The pipeline must verify the required outputs before moving an original and update the manifest with its new location.

Failed or incomplete documents remain available for retry.

### `metadata/`

Contains per-document JSON sidecars holding provenance information, including document identity, source URL, source type, manufacturer, document type, retrieval timestamp, and other relevant metadata.

The existing document IDs and sidecar filenames must remain stable during the reorganization.

### `processed/`

Contains normalized JSONL records generated by the extraction stage.

HTML and PDF processors may produce different record structures where necessary, but their outputs must follow the agreed record and provenance conventions.

### `chunked/`

Contains retrieval-ready JSONL chunks generated from processed records.

Chunking is a distinct stage from extraction. Chunk outputs, counts, and processing status must be tracked independently.

### `manifest.json`

The central registry for discovered source files and their ingestion lifecycle.

It records document identity, source location, file format, checksum, stage statuses, output references, timestamps, and errors.

The manifest is not a replacement for metadata sidecars or extracted records. It tracks pipeline state and relationships between artifacts.

## 3. Script Organization

Ingestion and source-processing scripts are organized under `scraper/scripts/`.

The scripts cover source collection, HTML processing, PDF processing, metadata generation, and chunking.

Shared functionality such as provenance validation and manifest operations should be implemented in reusable modules rather than duplicated across scripts.

The `scraper/vector_search/` directory remains responsible for embeddings, retrieval, and evaluation. Its existing evaluation baseline and artifacts must remain unaffected by the directory cleanup.

Tests remain under `scraper/tests/`, with path and import changes made as necessary following script relocation.

## 4. Manifest Ownership and Updates

A shared `manifest.py` module will own manifest loading, schema validation, registration, updates, and safe persistence.

Pipeline stages will report their own results through this shared interface rather than writing arbitrary portions of `manifest.json` directly.

Responsibilities are divided as follows:

- **Discovery:** identifies files, computes checksums, classifies formats, and registers new documents.
- **Metadata generation:** validates provenance and reports sidecar creation or review requirements.
- **Extraction:** reports validated extracted outputs, record counts, and errors.
- **Chunking:** reports validated chunk outputs, chunk counts, and errors.
- **Archival:** records successful archival and the updated source location.
- **Reconciliation:** compares manifest entries with actual files and identifies missing, stale, or ambiguous artifacts.

A stage is marked complete only after its required validations succeed. Existing artifacts must be reconciled before their status is marked complete during initial manifest creation.

## 5. Document Identity and Integrity

Each source document has one stable `document_id`.

Existing IDs must be preserved. New IDs may initially be derived from filenames, with collision detection to prevent accidental identity conflicts.

A SHA-256 checksum is recorded for each source file to identify content changes independently of filenames.

When source content changes, dependent metadata or processing outputs must be marked stale or pending until they are revalidated or regenerated.

Output filenames alone are not sufficient evidence that an artifact belongs to a particular source document.

## 6. Status Model

The manifest uses consistent status values:

- `pending`: not yet attempted or not yet verified.
- `in_progress`: currently being processed.
- `complete`: the stage and its required validations succeeded.
- `failed`: an attempted stage failed.
- `needs_review`: human review or clarification is required.
- `skipped`: a stage is deliberately not applicable or has been excluded.

Discovery also classifies unsupported file formats explicitly as `unsupported_format`. This classification is distinct from a processing failure.

For unsupported files, downstream stages remain unprocessed or are marked skipped as appropriate. If format support is introduced later, the document can be reclassified and processed.

## 7. Initial Manifest Bootstrap

A one-time bootstrap process will reconcile the existing corpus and create the initial manifest.

It will:

1. Inventory all source files in `incoming/`.
2. Preserve existing document IDs and provenance.
3. Match sources to existing sidecars, processed records, and chunks.
4. Validate relationships and output files where possible.
5. Populate checksums, counts, and verified statuses.
6. Flag ambiguous mappings, missing artifacts, duplicate IDs, and unsupported formats.
7. Generate a preview report before writing the manifest.

The bootstrap must not modify source documents, metadata sidecars, processed records, or chunks.

## 8. Safety and Recovery

Manifest updates must be validated and persisted safely. Interrupted writes must not corrupt the registry.

Retries must not create duplicate records or overwrite unrelated outputs.

Archival is permitted only after the required ingestion stages and validations succeed. Failed documents remain available for recovery.

Reconciliation should identify discrepancies between the manifest and filesystem without silently deleting files or rewriting established document identities.

## 9. Implementation Sequence

1. Reorganize the source-processing scripts and data directories.
2. Verify existing files and preserve all source and generated artifacts.
3. Commit the directory and documentation reorganization.
4. Implement the shared manifest interface and initial schema.
5. Bootstrap the manifest from existing artifacts and review the report.
6. Integrate manifest updates into each pipeline stage.
7. Test unsupported formats, failed processing, retries, changed sources, and archival.
8. Run the complete test suite and verify that existing retrieval and evaluation artifacts remain unchanged.

## 10. Scope Boundaries

The initial manifest covers source discovery, metadata, extraction, chunking, and archival.

Embedding generation, retrieval indexing, and evaluation remain separate workflows for now. They can be integrated into broader pipeline tracking later without expanding the initial schema unnecessarily.
