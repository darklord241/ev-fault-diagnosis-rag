## Result in brief

Ran the five shared candidate questions through the real local retrieval service and the Gemini-backed diagnosis pipeline. All five calls succeeded, all five reported `gemini-3.5-flash-lite`, and none used the deterministic fallback. The generated answers were consistent with the retrieved evidence in this small manual review. This is a useful baseline for comparison with the local Qwen run, not a statistically meaningful model ranking.

The existing MiniLM retrieval evaluation also completed successfully. It searched 891 candidate chunks across the same five questions and excluded 0 chunks for exceeding the 256-token limit. ## What these numbers do and do not mean

- `5/5 successful` and `5/5 Gemini reported` are directly observed API outcomes.
- The `grounding_score` is generated by the model itself. The 0.996 average is **not** an independently measured factuality or accuracy rate.
- The manual evidence review found support for these five answers, but the set is small and the questions are candidate cases without gold answer labels or gold evidence IDs. It cannot establish that Gemini is generally better than Qwen.
- The similarity scores in the retrieval report are cosine similarities, not calibrated probabilities or correctness scores.
- Gemini ignored the configured temperature of 0.2 because this model uses fixed sampling defaults. For a fair Qwen comparison, keep the same questions, retrieved evidence, prompt, top-k, and output schema; record each provider's effective sampling settings and do a human evidence check. If Qwen accepts the configured `0.2`, note that the decoding settings are not exactly matched.
- The exact Gemini API model tested is `gemini-3.5-flash-lite`. It is the fast/low-cost baseline configured in this checkout. A larger/slower Gemini model was not tested; no claim is made about its availability or performance with this key.

## Comparison with the local Qwen 3.5 9B run

Use the **same five inputs and the same retrieval pipeline** so the variable is the answer-generation model, not the corpus, embedding model, or retrieved context. In `agent-layer/.env`, your friend can set:

```dotenv
DEFAULT_LLM_PROVIDER=ollama
DEFAULT_LLM_MODEL=<exact model tag shown by ollama list>
OLLAMA_BASE_URL=http://localhost:11434
LLM_TEMPERATURE=0.2
```

Use the exact Qwen tag installed on their machine rather than assuming a tag spelling. Keep live retrieval enabled with the same corpus and embedding cache, restart the agent, and check `http://127.0.0.1:8000/api/v1/health` reports provider `ollama` and the selected Qwen model. Then run the evaluation command below. The Gemini-specific fixed-sampling caveat above applies.

For a stronger comparison, repeat each model run at least three times and report per-query latency plus median/mean, then have the same reviewer score answer correctness, evidence support, completeness, and unsafe/unsupported claims using the source chunks. Do not rank models on the self-reported grounding field alone.

## Reproduction

Start the backend and agent as described in the root `README.md`, with the corpus and local MiniLM model installed. Ensure the backend health endpoint reports `retrieval_ready: true`. The agent must have the intended model configured in its local `.env`; do not put API keys on the command line.

Retrieval-only evaluation:

```sh
PYTHONPATH=scraper agent-layer/.venv/bin/python -m vector_search.evaluate_retrieval \
  --top-k 5 \
  --output /tmp/evrag-minilm-evaluation.md
```

Live model evaluation through the same five cases:

```sh
agent-layer/.venv/bin/python dev-notes/model-test/run_live_model_evaluation.py \
  --top-k 5 \
  --output /tmp/evrag-live-model-evaluation.json
```

The live runner reads the model/provider from the running agent health route and sends requests only to the local backend gateway. The generated JSON contains per-query answer, model name, latency, retrieved source references, and aggregate counts. It does not read or print credentials.
